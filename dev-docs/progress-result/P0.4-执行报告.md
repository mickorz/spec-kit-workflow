## 关键发现与修复

### 1. run-tests.mjs 解析器漏判

**现象**：Round 1 的 49 个测试实际全部通过，但 evidence.json 记录 status=failed（"零测试"）。

**根因**：Node.js 内置 test runner 默认 spec reporter 输出 `ℹ tests N` 格式，run-tests.mjs 原解析器只支持 Jest/Mocha 的 `N passing` 格式。

**修复**：新增 `parseTestCounts()` 函数，支持：
- Node.js TAP: `# tests N`, `# pass N`, `# fail N`
- Node.js spec: `ℹ tests N`, `ℹ pass N`, `ℹ fail N`
- Jest/Mocha: `N passing`, `N failing`
- 兜底：计数 `✔`/`✖` 标记

**Agent 自主修复**：Round 2 的 Implement Agent 读取 findings.json 后，将 test 命令改为 `node --test --test-reporter=tap`，TAP 格式被解析器正确识别。

### 2. check-baseline.mjs 过度校验

**现象**：check-baseline.mjs 校验 tasks.md 哈希，但循环中 tasks.md 正常变化（标记 done、追加任务）。

**修复**：移除 tasks.md 校验，只校验 spec.md + traceability.json（审批后不可变的真相源）。

### 3. 循环机制验证

**关键路径**：Round 1 测试失败（假阴性）→ append-findings 追加 T-012 → Round 2 Agent 修复 → 收敛

这证明了循环的核心机制：
1. Test Runner 生成 evidence.json（即使假阴性也能触发循环）
2. is-converged.mjs 正确判定未收敛
3. append-findings.mjs 自动追加修复任务
4. Implement Agent 读取 findings 并修复问题
5. 第二轮收敛
