## 5. 问题分析

### 5.1 Reviewer 修改源码（根本问题）

**现象**：Reviewer Agent 使用 `agentType: 'general'`，拥有 write 工具。尽管 prompt 明确禁止修改源码，Reviewer 在 3/4 次审计中修改了 `src/auth.ts`。

**影响**：
1. review.json 基于修改后的代码，可能产生假阳性（FR-007）
2. backup/restore 机制检测到修改并恢复，但 review.json 已被污染

**已尝试的方案**：
- 设置文件只读属性（Windows ReadOnly）→ Reviewer 的 write 工具可覆盖只读文件，无效
- 改用 `agentType: 'explore'`（只读）→ explore agent 无法写 review.json
- base64 编码 + 分块写入 → 工作流沙箱中 `Buffer` 未定义，失败
- PowerShell here-string 管道 → 命令执行失败

**当前方案**：backup/restore + 完整性检测
- 审计前备份源码
- Reviewer 后快照对比
- 检测到修改则恢复 + 审计标记 codeUnchanged=false

**遗留问题**：review.json 可能基于修改后的代码，假阳性无法完全消除。

### 5.2 分类错误（contradicts vs partial）

**现象**：project-d 中 DEFAULT_LOCK_THRESHOLD=10（Spec 要求 5），Reviewer 发现矛盾（finding 中用了"矛盾"一词）但分类为 partial 而非 contradicts。

**根因**：Reviewer prompt 中 contradicts 的定义是"实现与 Spec 矛盾"，但 Reviewer 可能把"值不匹配"理解为"部分实现"而非"矛盾"。

**建议**：在 prompt 中增加 contradicts 的具体示例（如"参数值与 Spec 不一致 = contradicts"）。

## 6. 结论

### 6.1 核心结论

SDD Audit Workflow 在盲测条件下实现了 **100% 缺陷检出率**（9/9），所有注入的 missing/partial/contradicts 缺陷均被正确检出。假阳性仅 2 个，均由 Reviewer 修改源码这一已知问题导致，非审查逻辑缺陷。

### 6.2 用户核心需求达成

用户要求"确保 spec 的实现不要遗漏"——P0.7 证明：**审计模式零遗漏**，所有 Spec 需求逐条核对，注入的缺陷全部被检出。

### 6.3 待改进项

1. Reviewer 只读保护：需要从架构层面限制 Reviewer 的文件写入权限
2. contradicts 分类：需要更明确的分类指导
3. 一致性：project-a 审计 codeUnchanged=true，但 b/c/d 均 false，说明 Reviewer 行为非确定性
