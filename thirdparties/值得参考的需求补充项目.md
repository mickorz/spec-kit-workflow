有，而且我查到了几套比单纯“让 LLM 把 PRD 改写成 spec.md”更成熟的开源方案。

结合你的目标——把 PRD 转换成可追踪、可验证、不会静默遗漏需求的 Spec，再内化为 `opencode-dynamicworkflows` 的 `sdd.*` 函数——我最推荐优先研究下面 5 个项目。

## 一、最值得参考的开源项目

| 项目                | 最有价值的能力                        | 推荐程度 |
| ----------------- | ------------------------------ | ---- |
| BMAD Method       | PRD → 结构化 Spec、假设及开放问题、稳定能力 ID | 首选   |
| cc-sdd            | 需求发现、EARS 规范、复杂需求拆成多个 Spec     | 首选   |
| GitHub Spec Kit   | 澄清歧义、需求质量清单、跨文档一致性检查           | 强烈推荐 |
| OpenSpec          | 可测试行为场景、增量 Spec、需求变更管理         | 推荐   |
| Spec Workflow MCP | 需求 → 设计 → 任务的审批和产物管理           | 补充参考 |

其中，BMAD 是最直接对口“PRD → Spec”的项目。它已经将 PRD 和 Spec 明确拆成不同的职责：PRD 解释产品要做什么及为什么做；Spec 则是实现阶段消费的具体行为契约。

cc-sdd 更适合研究如何把需求写得精确、可验证，GitHub Spec Kit 则适合研究 Spec 生成后如何检查质量。

## 二、逐个看：真正值得研究的实现

### 1.&#x20;

BMAD Method

&#x20;— PRD → Spec 最直接

GitHub：[bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)

MIT License · 专门提供 `bmad-prd`、`bmad-spec` 两项能力

我读了它的 [`skills/bmad-spec/SKILL.md`](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/skills/bmad-spec/SKILL.md)，这部分尤其值得你深入看。

它允许输入 PRD、GDD、会议记录、RFC、产品 Brief，以及混合来源材料，然后整理成一份面向开发的 Spec。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



最有价值的不是生成模板，而是以下机制：

| 实际机制                        | 对你的借鉴价值                          |
| --------------------------- | -------------------------------- |
| Claim-by-claim Preservation | 逐条扫描来源内容，检查重要信息是否在 Spec 或附属文档中保留 |
| `.memlog.md`                | 以追加记录方式保存决策、约束、假设和需求变更           |
| 稳定 `CAP-N` ID               | Spec 修改时保持能力标识稳定                 |
| `companions`                | 大型 PRD 的图表、术语、状态机不必全部塞进 spec.md  |
| 双阶段自检                       | 分别检查 Spec 一致性，以及源内容是否被遗漏         |

它的 Spec 模板采用五个核心字段：Why、Capabilities、Constraints、Non-goals 和 Success signal。

不过，你现有的 Spec 使用 `FR / AC / NFR` 体系，因此借鉴转换算法和保真检查，不要直接替换你的 Spec 格式。

最值得阅读的两个文件是 [bmad-spec/SKILL.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/skills/bmad-spec/SKILL.md) 和 [spec-template.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/skills/bmad-spec/assets/spec-template.md)。

### 2.&#x20;

cc-sdd

&#x20;— 把模糊需求变成可测试行为

GitHub：[gotalab/cc-sdd](https://github.com/gotalab/cc-sdd) · MIT License

它的重点是 Requirements Engineering（需求工程）。

它使用 EARS（Easy Approach to Requirements Syntax）格式，把自然语言需求规范为明确的触发条件、系统行为和预期结果。

例如原始 PRD 写的是：

> 背包满了之后不能添加物品。

可以转换成：

```
FR-008: 背包容量限制

AC-021:
When 背包所有格子已满，
且不存在可继续堆叠的目标物品时，
系统 SHALL 拒绝新增物品，
并保持原有背包状态不变。
```

上面是我根据其 EARS 模板编写的示例，不是项目原文。

它的 [`requirements-review-gate.md`](https://github.com/gotalab/cc-sdd/blob/main/.kiro/settings/rules/requirements-review-gate.md) 还要求在写入正式 Requirements 前检查正常流程、异常流程、边界条件、可测试性、重复需求以及含糊用词。

对你的游戏需求场景尤其有价值的是 [`kiro-spec-batch`](https://github.com/gotalab/cc-sdd/blob/main/tools/cc-sdd/templates/agents/opencode-skills/skills/kiro-spec-batch/SKILL.md)：它可以根据 Roadmap 把较大的功能集合拆成多个 Spec，再检查多个 Spec 之间的数据模型、接口和职责是否冲突。

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub

+1



这部分适合未来的游戏系统 PRD：

`背包总 PRD → 背包客户端 Spec / 服务端 Spec / UI Spec / 配置 Spec / 协议 Spec`

但这类拆分必须保留来源归属，避免一个需求跨多个 Spec 时被重复或漏掉。

### 3.&#x20;

GitHub Spec Kit

&#x20;— Spec 质量门禁最值得借鉴

GitHub：[github/spec-kit](https://github.com/github/spec-kit) · MIT License

它有三个你当前特别需要研究的命令：

| 命令          | 值得参考的机制                     |
| ----------- | --------------------------- |
| `specify`   | 从原始描述生成需求、验收场景，并自检质量        |
| `clarify`   | 用结构化维度扫描歧义，优先澄清高影响问题        |
| `checklist` | 对 Spec 本身做完整性、清晰性、一致性、可测性检查 |

我直接读了其 Prompt 源码：

- [specify.md](https://github.com/github/spec-kit/blob/main/templates/commands/specify.md)
- [clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)
- [checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)

其中 `checklist` 有个很好的设计理念：先测试需求文档的质量，而不是测试代码实现。它会提出类似“异常流程是否都有明确要求”“边界条件是否完整”等审核问题。

### 4.&#x20;

OpenSpec

&#x20;— Spec 场景化与增量变更

GitHub：[Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec) · MIT License

它特别强调一个 Requirement 必须能够用明确的 Scenario 表达，并推荐 Given / When / Then 格式。

另一个核心特性是 Delta Spec：`ADDED / MODIFIED / REMOVED`，只描述本次需求变化，而不是每次重新生成整个 Spec。

这点适合你以后处理：

> 给已经开发完成的背包系统增加自动整理功能。

不用重写原背包 Spec，而是生成此次变更的 Delta，验收完成后再合并回主 Spec。

## 三、结合你的 Dynamic Workflows，最值得组合哪些机制？

我不建议选一个项目整体搬运，而是把各自最强的部分组合成你自己的需求转换能力。

| 你的目标函数                        | 优先参考                                         |
| ----------------------------- | -------------------------------------------- |
| `sdd.intake()`                | BMAD 的来源内容逐条保留机制                             |
| `sdd.clarify()`               | GitHub Spec Kit 的歧义分类与问题优先级                  |
| `sdd.specify()`               | BMAD 的结构化转换 + cc-sdd 的 EARS                  |
| `sdd.validateSpec()`          | Spec Kit 的 Spec 质量 Checklist                 |
| `sdd.analyzeSourceCoverage()` | BMAD 的 Preservation 检查 + 你自己的 SRC → FR/AC 映射 |
| `sdd.updateSpec()`            | OpenSpec 的 Delta Spec 机制                     |

其中最值得你自己开发、而不是直接借用现成 Prompt 的，是 Source Coverage Gate。

因为这些项目虽然有来源保留、质量审查、需求覆盖检查等机制，但我没有在所查实现中发现一套直接符合你现有 `SRC → FR/AC/NFR → Tasks → Code` 的完整确定性映射协议。

你的差异化能力可以放在这里。

## 四、推荐的最终需求转换链

原始 PRD / 用户需求

Markdown、GDD、自然语言及关联资料

Intake — 保留原始信息

逐条提取 SRC-ID、来源位置、事实、约束

Clarify — 澄清与裁决

歧义、冲突、关键缺失信息、明确排除项

Specify — 生成规格

FR / AC / NFR、EARS 行为表述及验收场景

Source Coverage + Quality Gate

遗漏、错译、无依据新增、不可测试、来源冲突

经过批准的 spec.md

进入 Plan → Tasks → Implement → Review → Converge

特别建议保留双向检查：

PRD → Spec： 每一条原始需求都有明确的覆盖、排除或待确认结果。

Spec → PRD： 每一条正式需求都能说明来自哪里；如果是 Agent 补充的边界条件，也必须标记为推导项，而不是伪装成 PRD 原文。

这两种检查结合，才能同时发现需求遗漏和 AI 擅自增加需求的问题。

## 五、我的研究优先级建议

如果只深入研究三份源码，我会按这个顺序：

1

[BMAD bmad-spec/SKILL.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/skills/bmad-spec/SKILL.md)

学习 PRD/GDD 多源转换、逐条保真检查、假设与决策记录。

2

[cc-sdd requirements-review-gate.md](https://github.com/gotalab/cc-sdd/blob/main/.kiro/settings/rules/requirements-review-gate.md)

学习把含糊业务描述变成可测试需求，以及生成前的质量审查。

3

[Spec Kit clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)

学习怎样识别真正需要用户决策的需求歧义，避免无意义的反复提问。

最终建议：优先研究 BMAD 的 `bmad-spec`。 它最接近你想补齐的“复杂 PRD → 高保真 Spec”这一环，尤其是逐条来源保留和双阶段检查机制。

随后用 cc-sdd 的 EARS 把结果规范化成你现有的 FR/AC/NFR，再用 Spec Kit 的 Checklist 做质量门禁。

这样就不必重新设计 `sdd.feature()` 的后半段，而是重点增强前半段：让送入自动开发流程的 Spec 本身更加完整、明确、可验证。
